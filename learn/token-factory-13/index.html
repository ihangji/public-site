13 资产周期

Token 工厂拆解手册：从 GPU、推理服务到合同与现金流第三部分 算力底座约 39 分钟更新于 2026-08-04

13.1 三只时钟

硬件资产不是在交付日一次性成立，而是在三只钟之间不断重估：物理寿命回答硬件是否还能通电运行，技术寿命回答它是否仍支持目标模型、精度、上下文和互联要求，经济寿命回答它在电费、租金、运维和售价约束下是否仍产生正向贡献。三者没有固定顺序：一台旧设备物理完好，可能因显存不足无法承载新模型；也可能在新模型上继续跑低延迟小模型或批量任务，延长经济寿命；新设备也可能因为没有液冷、网络或客户负载而长期闲置。残值必须落到可运行、可销售、可回收三个情景，不能套统一百分比。

录音中把海外采购价、国内租金和五年租期连成收益逻辑时，最需要补的就是时间轴：新架构何时交付，可销售负载如何变化，客户承诺多长，上游租约多长，设备在哪个时间点可以转售。当前价格差只是一张截面，不能自动延伸为五年现金流。

13.2 代际速度

五年租约的最大隐患是硬件代际比租约短。近年的公开节奏：Hopper 代之后是 Blackwell 代，再到 Blackwell Ultra（B300 与 GB300），下一代 Rubin 已在路线图上并预计 2026 年下半年出货。核以大致一年到一年半一代计，一份五年租约要跨越三到四个代际。

13.3 参数膨胀

模型参数增长快于单卡显存增长，这是弃租风险的技术来源。公开事实的对照：2026 年 7 月的 Kimi K3 为 2.8 万亿参数，原生 MXFP4 权重体积约 594 GB，自托管的最低硬件门槛被描述为八张 H100 80GB 起；核同期阿里预告 2.4 万亿参数的开放权重模型；核而 B300 单卡显存 288 GB、整机约 2.3 TB。模型规模两年上了一个数量级，单卡显存同期翻了不到一倍。缓解因素有两个：MoE 结构让激活参数远小于总参数，量化把每参数字节压到四分之一甚至更低，这两项让硬件门槛的上升慢于参数增长，但方向没有变。

模型一年比一年大，卡的显存涨得慢得多。我们租五年的机器，第三年可能就跑不动当红模型了。

13.4 恢复链条

设备故障本身通常很短：监控报错、掉卡或节点退出。拉长停机的往往是组织之间的等待：平台发现并隔离，远程团队诊断，厂商批准返修授权，备件发货，本地人员获得准入并更换，烧机、重新加入集群，最后才恢复客户容量。厂商的公开支持条款区分初始响应、高级返修、现场服务和现场备件：最高严重级别可以有一小时初始响应目标，但那表示开始响应，不表示一小时修复；返修与现场服务还受覆盖国家、审批、截单时间和地区条件限制，现场备件是附加服务且与购买公司关联，资产或服务关系改变可能影响资格。核这带来一个常被忽略的问题：租到设备的人未必是支持合同的权利人，能进机房的人未必有厂商授权，厂商同意换件也不意味着备件已经清关到场。运维尽调要沿同一台设备的序列号，把资产合同、支持权益、返修地址、授权联系人和机房准入串起来。

图 26停机时钟的八段
段长为常见比例示意，跨境场景下备件与入场两段通常更长。
别问多久能修好，问这八段各由谁负责、每段的时钟从哪一刻开始走。

录音中提出每个容量中心安排自有运维人员、解决 72 小时运维问题。录方向正确：远程平台不能替代现场动作。但 72 小时没有定义从何时起算、到什么状态结束。一个可审计的恢复时钟至少拆八段。

  1. 故障发生至监控发现
  2. 发现至工单受理
  3. 受理至远程诊断完成
  4. 诊断至厂商批准返修
  5. 批准至备件到场
  6. 到场至工程师获准入场
  7. 更换至烧机重入集群
  8. 重入至客户容量与服务目标恢复

每一段都要标清楚算工作日还是自然日，用哪个时区，遇节假日怎么办，以及物流清关和机房审批算在哪一段里。合同卖的是 token 服务，终点就应写成客户可用容量恢复，而不是工程师已到场或新卡已插入。本地招了人也不等于本地能修：进机房、开机柜、执行厂商流程、接触管理网络是四组独立权限，一名当地员工只有在值班覆盖、技能、准入、授权、备件和升级路径同时成立时才形成恢复能力；判断标准是控制接口和历史表现，不是自有还是外包的标签。

上游承诺与客户恢复之间还有差额：厂商可能只承诺开始响应、备件到场或单机恢复，客户要的是 token 服务恢复。模型副本重新上线后，排队请求、生成状态、计量事件和账单仍可能不完整，这段差额由服务运营方补齐。上游 99.99% 也不能直接转卖：云厂的可用性承诺有明确对象、配置、计算窗口、排除项和救济方式，区域级承诺要求跨可用区部署，抵扣通常只抵未来服务费。核上游协议达标，不能自动证明端到端 token 服务达标。

13.5 备件保险

备件是用库存换恢复时间：备用 GPU、电源、交换模块和液冷部件占用现金，也随架构迭代贬值；不备件，则把恢复时间交给物流、海关和厂商库存。备件比例由故障率、到件分布、集群冗余、客户 SLA 和设备替代性共同决定。技术上可以用 N+1 冗余维持服务，商业上要决定谁为冗余买单：销售按满载容量报价、运维又要保留故障缓冲，同一批卡就被重复销售了，可售容量必须先扣除计划维护、故障冗余和压力余量。备件账至少记录位置、序列号、兼容版本、归属、可更换权限和调拨时长：备用件在另一个国家，不能按现场备件计入恢复模型。

保险转移的是保单定义的损失，不是业务风险本身。设备险、运输险、业务中断险和责任险可能由不同主体购买，是否赔付取决于触发条件、等待期、免赔额、地域和被保险人身份。已经上保险只是一条索引，核验要看保单、批单、设备清单和理赔流程，尤其要核对收入由销售主体取得、资产由另一主体持有时，谁有可保利益、谁能主张停机损失。

13.6 状态管理

财务台账记录购置日、原值、折旧和账面净值；运营台账还要记录资产此刻能做什么。建议至少九种状态：待交付、在途、待上架、验收中、可调度、降额运行、隔离诊断、等待备件、退役待处置，状态变化带时间、原因、责任人、客户影响和证据链接。状态机能暴露两个常见问题：设备在账面上是固定资产，却长期停在待上架或等待备件，仍被收入模型当成满载产能；降额节点还能运行，却被按正常规格出售，尾延迟和故障率转嫁给了客户。可售容量应从运行状态实时汇总，而不是从采购数量静态推算。

资产台账应能回答十二个问题：型号和序列号；所有权与留置权；设备在哪个机柜；谁能进场；谁有带外和集群权限；支持权益属于谁；覆盖哪个国家和期限；哪些部件可自行更换；备件在哪里；返修每段时钟多长；故障时如何保持客户容量；租约、客户合同和预期技术寿命是否匹配。有一问答不上来，不必立刻否定资产，但应把它从确定产能降为待验证容量。区域迁移和退出也要提前设计。迁移的对象是一整套依赖：运输保险、进出口手续、机柜与液冷兼容、支持权益、管理员权限、客户合同与计量基线。退出则要验证权重、日志、计量和客户数据怎样导出，密钥怎样撤销，备用站点多久能接管。没有退出设计，长期合同看似稳定，实际是把技术控制权抵押给单一上游。

注意第三行：租赁并不能规避需求风险，只能规避资产贬值风险。市场需求下滑时，自购方可以停机减少电费与运维，租赁方仍要按月付租。把租赁理解为轻资产因此低风险，是这个模式里最常见的误解。

显存、拓扑、电力与恢复能力共同限定可售产能，设备寿命和市场变化又给它加上有效期。第四部分转到软件层，看同一批硬件在推理系统里能兑现多少。
