28.1 交付锁定

技术团队可以证明模型返回了结果，客户仍可能拒绝付款；销售可以签下 99.9% 的 SLA，运营团队也可能不知道怎样测。合同要把产品、计量、性能、数据和故障写成双方可观察、可对账、可执行的条件。订单先用产品代码锁定可购买对象，再明确模型和版本、区域、交付形态、容量、期限与开始计费条件：GPU 租赁的验收对象是健康实例，专用端点是指定模型与容量，MaaS 是 API 与用量，聚合路由还要说明底层供应商选择和回退边界。产品边界不清会直接污染账单：合同写 token 服务、实际按保留 GPU 收费，双方对闲置承担者的理解就不同；合同写指定区域、路由又能跨区回退，数据和 SLA 责任就不一致。

28.2 计量条款

计量必须能复现。最小计量条款包括：模型、分词器与计数实现；输入、输出、缓存、推理和工具怎样计费；失败、取消、超时、重试与回退是否收费；用量时区、账期、币种、汇率、税与手续费；双方日志冲突时以哪组记录为准。计量会反向影响系统：失败重试收费，客户会要求幂等和重试标识；缓存输入有折扣，客户会改提示词结构；批处理更便宜，非实时负载会迁移。合同不是被动记录商业模式，它会改变负载。渠道结构会增加两次对账（客户与渠道、渠道与底层提供商），必须用同一请求 ID 连接请求、供应商、token 和账单，否则回退一次可能触发两笔上游成本。

28.3 承诺补偿

SLO、SLA 与补偿要分开写。一条可执行的 SLA 至少回答：对哪个模型、区域、端点组合；用什么窗口计算；首字、出字、错误率和可用性分别怎样定义；计划维护、客户配置、第三方网络、超限和不可抗力怎样处理；客户多久内提出索赔、用什么证据；补偿是现金、退款还是未来账单信用、是否为唯一救济。公开条款可作参照：头部云厂对不同服务设不同目标、以分钟级服务端错误界定停机、要求按条件申请信用；服务信用条款普遍写明信用额不是现金、通常不可转让且可能到期。核有服务信用不等于客户业务损失被覆盖，这一点在向下游转售 SLA 时尤其要向客户讲清楚。

28.4 验收账单

账单之前还有验收。新部署应有独立验收阶段：固定模型和版本、硬件或端点、长度分布、并发、持续时间、延迟分位数、错误率、原始日志和计算脚本，验收通过后才进入起租或承诺期，避免供应商在调试阶段收费、客户在生产阶段继续改基线。性能数字必须与合同对象一致：内部内核指标不能替代端到端延迟，平均值不能替代 P95 与 P99，静态批量测试不能替代动态请求。

28.5 结算路径

结算不仅是单价乘用量，还要处理预付、最低消费、账期、信用额度、税、跨币种、手续费和服务信用。收入确认与现金到达可能不同：预付款先收到钱但仍有未履行义务，账期收入已开票却可能形成应收和坏账。数据条款要沿真实路径写：分别处理提示词与响应、缓存、运维日志、账单和支持工单，写清保留、训练用途、访问、分包商、地域、删除和导出；聚合路由场景不能只看入口平台的政策，还要看实际底层供应商。数据要求有二阶成本：禁止保留内容会降低调试和争议复核能力，固定区域会减少可用供应商和回退空间，合规不是免费标签，应进入产品范围和价格。

28.6 退出设计

退出条款决定风险能否收口。模型会弃用，价格会变化，客户负载会迁移，硬件也会迭代，合同要定义价格变更通知、模型版本迁移、余额和信用处理、数据导出、密钥吊销、最低承诺剩余款、终止协助和争议窗口。退出不是悲观附录：它的直接作用是限制终止损失，间接作用是改善合作期间的激励，客户知道能取回数据才更愿意迁入，供应商知道最低承诺怎样处理才敢为客户预留容量。合同审查最后用五张表收口：收入表核费率与价格变更，成本表核上游传导，资产表核设备、模型权利、日志和余额归属，风险表核性能、数据、坏账、汇率和退出的承担方，激励表核双方冲突有没有边界、证据和价格。好的合同不消灭冲突，而是让冲突有边界、证据和价格。

追问每个可测条款对应哪个指标、哪个数据源、谁的日志说了算；赔付封顶在什么水平；退出时数据和余额怎么处理。
